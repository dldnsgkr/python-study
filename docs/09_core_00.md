# 00 · 실행 모델과 작업 환경

`interpreter · bytecode · venv · style`

파이썬 코드가 실행되기까지는 세 단계를 거칩니다. **소스 → 바이트코드 → 인터프리터 루프**. 컴파일은 사라진 게 아니라 눈에 안 보일 뿐입니다. `.pyc`는 이 중간 산출물이고 `__pycache__`에 캐시됩니다.

*바이트코드 직접 들여다보기*

```python
import dis

def add_tax(price):
    return price * 1.1

dis.dis(add_tax)
# LOAD_FAST     price
# LOAD_CONST    1.1
# BINARY_OP     5 (*)
# RETURN_VALUE
```

여기서 이미 파이썬의 성격이 드러납니다. `price`의 타입은 어디에도 없습니다. `BINARY_OP *`는 실행 시점에 `price` 객체에게 "곱셈 할 줄 아니?"라고 묻습니다. 이것이 **동적 타이핑**이자 뒤에 나올 **프로토콜 기반 설계**의 뿌리입니다.

**☕ JVM 개발자 노트**

JVM에서 `javac`가 잡아 주던 오류를 파이썬에서는 아무도 대신 잡아 주지 않습니다. 그래서 실무 파이썬은 **타입 힌트 + mypy(또는 pyright) + pytest**를 컴파일러 대용으로 씁니다. 15·18파트에서 이 조합을 다룹니다. "타입 없는 언어"가 아니라 "타입 검사를 개발자가 켜서 쓰는 언어"로 보는 편이 정확합니다.

## 환경: 프로젝트마다 격리된 인터프리터

파이썬은 의존성을 *인터프리터별로* 설치합니다. 전역에 설치하면 프로젝트끼리 버전이 충돌합니다. 그래서 가상환경은 선택이 아니라 기본값입니다.

*bash*

```bash
# 표준 방식
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 요즘 팀에서 많이 쓰는 방식 (uv: 해석·설치가 훨씬 빠름)
uv venv
uv pip install fastapi
uv run python main.py
```

의존성 선언은 `pyproject.toml` 한 곳으로 모읍니다. Gradle의 `build.gradle.kts`에 해당하는 파일입니다.

*pyproject.toml*

```toml
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27", "pydantic>=2.7"]

[project.optional-dependencies]
dev = ["pytest", "mypy", "ruff"]

[tool.ruff]
line-length = 100
```

**💡 Tip**

포매터·린터는 **ruff** 하나로 통일하는 게 현재 표준에 가깝습니다(black + isort + flake8 대체). `ruff format .`과 `ruff check --fix .` 두 명령이면 끝입니다.

## 스타일: PEP 8은 협업 프로토콜

- 들여쓰기 **공백 4칸**. 탭과 섞으면 `TabError`.
- 변수·함수 `snake_case`, 클래스 `PascalCase`, 상수 `UPPER_SNAKE`.
- 내부용은 `_name`, 서브클래스 충돌을 피하려면 `__name`(이름 맹글링).
- 모듈 파일명은 `lower_snake.py`, 한 줄 100자 내외.

**🖥 REPL 퀴즈 — 00-1 · 출력 예측**

```python
>>> import sys
>>> type(sys.modules)
>>> 'json' in sys.modules
>>> import json
>>> 'json' in sys.modules
```

---

**🟢 출력 보기**

```text
<class 'dict'>
False
True
```

import는 선언이 아니라 **실행문**입니다. 모듈을 찾아 실행하고 그 결과 객체를 `sys.modules`에 캐시한 뒤, 현재 네임스페이스에 이름을 바인딩합니다. 14파트에서 자세히 다룹니다.

---

**🟢 2번 해설**

`x + 1`은 `BINARY_OP` 하나로 끝나지만 `x.__add__(1)`은 `LOAD_ATTR`(속성 조회) → `CALL`(호출) 두 단계를 거칩니다. 연산자는 단순한 문법 설탕이 아니라, 인스턴스 속성 조회를 건너뛰고 **타입 슬롯**을 직접 참조하는 최적화 경로입니다. 그래서 인스턴스에 `__add__`를 나중에 붙여도 `+`는 그걸 보지 못합니다(11파트).
