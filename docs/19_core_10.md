# 10 · 클래스 — 속성 조회의 규칙

`self · MRO · property · descriptor`

*기본 구조*

```text
class Account:
    bank = "KB"                      # 클래스 속성 — 모든 인스턴스가 공유

    def __init__(self, owner: str, balance: int = 0):
        self.owner = owner           # 인스턴스 속성
        self._balance = balance      # 관례상 내부용

    def deposit(self, amount: int) -> None:
        self._balance += amount

    @property
    def balance(self) -> int:        # 게터: account.balance 로 접근
        return self._balance

    @classmethod
    def from_row(cls, row: dict) -> "Account":     # 대안 생성자
        return cls(row["owner"], row["balance"])

    @staticmethod
    def is_valid_owner(name: str) -> bool:
        return bool(name.strip())

    def __repr__(self) -> str:
        return f"Account(owner={self.owner!r}, balance={self._balance})"
```

`self`는 예약어가 아니라 **첫 번째 위치 인자**일 뿐입니다. `a.deposit(100)`은 `Account.deposit(a, 100)`으로 변환됩니다. 이 변환을 수행하는 게 다음 파트의 디스크립터 프로토콜입니다.

## 속성 조회 순서

`obj.x`를 평가할 때 파이썬은 이 순서로 찾습니다.

1. 타입의 MRO에서 **데이터 디스크립터**(`__get__`+`__set__`) — `property`가 여기
2. 인스턴스 `__dict__`
3. 타입의 MRO에서 일반 클래스 속성 / 비데이터 디스크립터(메서드)
4. 없으면 `__getattr__` 호출 → 그것도 없으면 `AttributeError`

**⚠️ Gotcha**

클래스 속성에 가변 객체를 두면 **모든 인스턴스가 공유**합니다.

```python
class Cart:
    items = []          # 위험!  모든 장바구니가 같은 리스트를 쓴다

    def add(self, x):
        self.items.append(x)      # 조회는 클래스 속성, 변경도 그 객체에 반영
```

반드시 `__init__` 안에서 `self.items = []`로 만드세요. 참고로 `self.items = self.items + [x]`는 대입이라 인스턴스 속성을 새로 만들어 버려서 또 다른 혼란을 낳습니다.

## 상속과 MRO

*super · MRO*

```python
class Base:
    def setup(self): print("Base")

class A(Base):
    def setup(self):
        super().setup()          # 부모가 아니라 'MRO상 다음' 클래스
        print("A")

class B(Base):
    def setup(self):
        super().setup()
        print("B")

class C(A, B): pass

C().setup()          # Base → B → A 순으로 출력
print([c.__name__ for c in C.__mro__])   # C, A, B, Base, object
```

`super()`는 "부모 클래스"가 아니라 **MRO에서 자기 다음 차례**를 가리킵니다. C3 선형화 알고리즘이 순서를 정하며, 이 덕분에 다중 상속에서 `Base.setup`이 한 번만 호출됩니다(다이아몬드 문제 해결).

**☕ JVM 개발자 노트**

파이썬은 다중 상속을 허용하고 인터페이스라는 별도 문법이 없습니다. Java의 `interface`는 `abc.ABC` 또는 `typing.Protocol`로 표현합니다(12파트). 접근 제어자도 없어서 `private`은 `_name` 관례일 뿐입니다. `__name`은 `_ClassName__name`으로 이름이 바뀌는 **맹글링**이며 은닉이 아니라 서브클래스 충돌 방지 장치입니다.

## property와 검증

*property*

```python
class Product:
    def __init__(self, price: int):
        self.price = price            # 여기서도 세터가 호출된다

    @property
    def price(self) -> int:
        return self._price

    @price.setter
    def price(self, value: int) -> None:
        if value < 0:
            raise ValueError("가격은 음수일 수 없습니다")
        self._price = value
```

파이썬에서는 처음부터 게터·세터를 만들지 않습니다. 공개 속성으로 시작하고, **검증이나 계산이 필요해지는 순간 property로 바꿔도 호출부가 그대로**이기 때문입니다. 이것이 파이썬에 롬복류 보일러플레이트가 필요 없는 이유입니다.

**🖥 REPL 퀴즈 — 10-1 · 클래스 속성과 인스턴스 속성**

```python
>>> class C:
...     x = 1
>>> a, b = C(), C()
>>> a.x = 100
>>> C.x, a.x, b.x
>>> C.x = 50
>>> C.x, a.x, b.x
```

---

**🟢 출력 보기**

```text
(1, 100, 1)
(50, 100, 50)
```

`a.x = 100`은 클래스 속성을 바꾸는 게 아니라 **a의 인스턴스 사전에 새 항목을 만듭니다**(섀도잉). 이후 `a.x`는 인스턴스 사전에서 먼저 발견되므로 클래스 값 변경에 영향을 받지 않습니다. b는 계속 클래스 속성을 봅니다.

**🟢 1번 예시 답**

```python
class Temperature:
    def __init__(self, celsius: float = 0.0):
        self.celsius = celsius

    @property
    def fahrenheit(self) -> float:
        return self.celsius * 9 / 5 + 32

    @fahrenheit.setter
    def fahrenheit(self, value: float) -> None:
        self.celsius = (value - 32) * 5 / 9
```

3번 힌트: `__getattr__`은 **일반 조회가 실패한 뒤에만** 불리고, `__getattribute__`는 **모든 속성 접근마다** 불립니다. 후자를 잘못 구현하면 무한 재귀에 빠지므로 내부에서 `object.__getattribute__(self, name)`을 써야 합니다.
